# RESQPERATION and TrackingAid Request Integration Guide

This guide documents the complete request flow between RESQPERATION, EvaTrack, and TrackingAid.

The purpose of the integration is simple:

- EvaTrack or RESQPERATION users can create resource/personnel requests.
- RESQPERATION receives the request first and acts as the HQ validation point.
- HQ/Admin validates, returns, rejects, or forwards the request.
- Approved requests are forwarded to TrackingAid.
- RESQPERATION can read TrackingAid resource inventory so HQ can see what resources are available before forwarding requests.

This is written for the capstone workflow. Keep the implementation beginner-friendly, database-driven, and easy to verify through SQL.

## 1. System Responsibilities

| System | Responsibility |
| --- | --- |
| EvaTrack | Can send evacuation/resource/personnel requests to RESQPERATION. |
| RESQPERATION | Receives requests, validates them, records audit logs, and forwards approved requests to TrackingAid. |
| TrackingAid | Receives forwarded requests from RESQPERATION and exposes available resources/inventory for RESQPERATION to view. |

Important distinction:

- `request_source` / `source_system` means where the request originally came from, such as `EvaTrack` or `ResQperation`.
- `requested_by` means who asked for the resource, such as an evacuation center staff member, rescuer, or HQ desk.
- `forwarded_by_*` means which RESQPERATION user approved and forwarded the request to TrackingAid.

## 2. Environment Requirements

RESQPERATION uses two database connections:

- Main RESQPERATION shared DB, configured by the normal Laravel `DB_*` variables.
- TrackingAid DB, configured by the `TRACKINGAID_*` variables.

Add or keep these variables in `backend-laravel/.env`.

```env
TRACKINGAID_DB_CONNECTION=mysql
TRACKINGAID_DB_HOST=<TrackingAid laptop IP or database host>
TRACKINGAID_DB_PORT=3306
TRACKINGAID_DB_DATABASE=trackingaid_db
TRACKINGAID_DB_USERNAME=<trackingaid user>
TRACKINGAID_DB_PASSWORD=<trackingaid password>
TRACKINGAID_DB_TIMEOUT=5
TRACKINGAID_FORWARD_TABLE=resqperation_forwarded_requests

EXTERNAL_REQUEST_INTAKE_KEY=<shared secret key for EvaTrack or external request senders>
```

After editing `.env`, run:

```bash
cd C:\backend\G10CAPSTONE\resqperation-system\backend-laravel
php artisan config:clear
```

Test the TrackingAid connection:

```bash
php artisan tinker --execute "dump(DB::connection('trackingaid')->select('SELECT DATABASE() AS db_name, CURRENT_USER() AS current_user'));"
```

If this fails, the problem is network/firewall/MySQL permission, not the RESQPERATION request code.

## 3. Required TrackingAid Permissions

The TrackingAid database user must allow RESQPERATION to:

- read TrackingAid resources/inventory
- create or update the handoff table
- insert forwarded request rows

Recommended minimum permissions:

```sql
GRANT SELECT ON trackingaid_db.inventory TO 'trackingaid_remote'@'%';
GRANT SELECT ON trackingaid_db.items TO 'trackingaid_remote'@'%';
GRANT SELECT ON trackingaid_db.requests TO 'trackingaid_remote'@'%';
GRANT SELECT, INSERT, UPDATE, CREATE, ALTER ON trackingaid_db.resqperation_forwarded_requests TO 'trackingaid_remote'@'%';
FLUSH PRIVILEGES;
```

If TrackingAid wants one simpler permission during development:

```sql
GRANT SELECT, INSERT, UPDATE, CREATE, ALTER ON trackingaid_db.* TO 'trackingaid_remote'@'%';
FLUSH PRIVILEGES;
```

Use stricter permissions before final deployment.

## 6. Incoming Requests From EvaTrack

EvaTrack can send requests into RESQPERATION using:

```http
POST /api/v1/external/resource-requests
X-RESQPERATION-INTEGRATION-KEY: <shared external request key>
Content-Type: application/json
```

Alternative auth:

```http
Authorization: Bearer <shared external request key>
```

Example EvaTrack payload:

```json
{
  "source_system": "EvaTrack",
  "source_reference": "EVAT-20260702-0001",
  "request_category": "resource",
  "requested_item": "Food packs",
  "resource_type": "Food packs",
  "quantity": 25,
  "unit": "packs",
  "priority": "High",
  "requested_by": "EvaTrack evacuation personnel",
  "evacuation_center_id": "EC-MAMBALING-001",
  "evacuation_center_name": "Mambaling Evacuation Center",
  "evacuation_center_address": "Barangay Mambaling, Cebu City",
  "description": "Families from coastal sitio need food packs after evacuation.",
  "requested_at": "2026-07-02 19:30:00"
}
```

RESQPERATION stores this in `resource_requests` with:

- `request_source` = `evatrack`
- `source_reference` = `EVAT-20260702-0001`
- `validation_status` = `needs_validation`

The pair `request_source + source_reference` prevents duplicate external requests. If EvaTrack sends the same source reference again, RESQPERATION updates the existing queue record instead of creating duplicates.

## 7. RESQPERATION Request Workflow

The user flow in RESQPERATION should be:

1. Request enters the validation queue.
2. HQ/Admin opens the request details.
3. HQ/Admin checks identity, location, urgency, quantity, duplicate risk, and available resources.
4. HQ/Admin chooses one correct action:
   - save validation
   - return request
   - reject/cancel request
   - forward to TrackingAid
5. If forwarded, RESQPERATION writes to:
   - main DB `resource_requests`
   - main DB validation/audit records
   - TrackingAid DB `resqperation_forwarded_requests`

The request should not be forwarded if it is returned or cancelled.

## 8. TrackingAid Resource Visibility In RESQPERATION

RESQPERATION reads resources from TrackingAid so HQ can see availability before forwarding.

Current TrackingAid tables checked by RESQPERATION:

- `inventory`
- `items`
- `requests`

The active mirror reads from `inventory` when it is available.

Expected minimum `inventory` columns:

| Column | Meaning |
| --- | --- |
| `id` | TrackingAid inventory row ID. |
| `name` | Resource name. |
| `category` | Resource category. |
| `sku` | Optional stock keeping reference. |
| `type` | Resource type/classification. |
| `quantity` | Available quantity. |
| `storage_location` | Where the resource is stored. |
| `expiration` | Optional expiration date. |
| `deleted_at` | Soft delete marker. |

TrackingAid resource query:

```sql
SELECT
  id,
  name,
  category,
  sku,
  type,
  quantity,
  storage_location,
  expiration,
  updated_at
FROM inventory
WHERE deleted_at IS NULL
ORDER BY quantity DESC, name ASC;
```

If the `inventory` table exists but has no rows, RESQPERATION shows an empty TrackingAid resource state. That means the connection is working, but TrackingAid has not added resource inventory yet.

## 9. TrackingAid Implementation Requirements

TrackingAid should implement these parts so the integration is useful:

### 9.1 Read forwarded requests

TrackingAid should display rows from `resqperation_forwarded_requests` as incoming validated requests from RESQPERATION.

Recommended TrackingAid workflow:

1. Read new rows where `resqperation_status = 'forwarded'`.
2. Show request source, quantity, area, urgency, requester, and RESQPERATION validation notes.
3. Allow TrackingAid to accept, prepare, release, deliver, or return the request.
4. Save their internal status in their own TrackingAid tables.

### 9.2 Expose resource inventory

TrackingAid should keep `inventory` updated with real resources.

Examples:

- food packs
- hygiene kits
- drinking water
- first aid kits
- medical responders
- ambulance units
- rescue vehicles
- rescue boats
- temporary shelter kits

### 9.3 Optional status callback later

For a stronger integration, TrackingAid can later expose or write back status fields such as:

- accepted by TrackingAid
- preparing
- released
- in transit
- delivered
- returned to RESQPERATION for clarification

For now, the current implemented integration focuses on request handoff and inventory visibility.

## 13. Test Cases

### 13.1 EvaTrack sends request

Expected result:

- RESQPERATION receives the request.
- Request appears in Resources and Requests validation queue.
- `resource_requests.validation_status` is `needs_validation`.

### 13.2 EvaTrack sends duplicate source reference

Expected result:

- Existing row updates.
- No duplicate request row is created for the same `request_source + source_reference`.

### 13.3 HQ validates request

Expected result:

- Request validation status changes based on decision.
- Validation/audit record is saved.

### 13.4 HQ forwards request to TrackingAid

Expected result:

- RESQPERATION request becomes `forwarded`.
- `tracking_reference` is saved.
- TrackingAid receives a row in `resqperation_forwarded_requests`.
- `forwarded_by_user_id`, `forwarded_by_name`, and `forwarded_by_role` are populated when an authenticated HQ/Admin user forwards it.

### 13.5 TrackingAid inventory is shown to RESQPERATION

Expected result:

- If TrackingAid `inventory` has rows, RESQPERATION displays those resources.
- If TrackingAid `inventory` is empty, RESQPERATION displays a real empty state instead of fake resources.

## 14. Security Rules

- Do not expose database passwords in Git.
- Keep shared keys in `.env`, not in frontend code.
- External systems must use `X-RESQPERATION-INTEGRATION-KEY`.
- Returned or cancelled requests must not be forwarded.
- RESQPERATION should audit validation and forwarding actions.
- TrackingAid should not overwrite RESQPERATION's main DB directly.
- RESQPERATION should not edit TrackingAid inventory; it only reads inventory and writes handoff requests.
