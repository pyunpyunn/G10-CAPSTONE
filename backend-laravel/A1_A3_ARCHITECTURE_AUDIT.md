# A1–A3 architecture audit — 2026-10-01

## Implementation update — 2026-10-02

The 2026-10-01 inventory below is historical and no longer describes the current tree. The latest local suite passes **87 tests and 361 assertions**. All service files now have fewer than 300 physical lines (largest: 296). TrackingAid forwarding no longer attempts DDL during a request. Inquiry, Dashboard, and Mapping success responses now pass through controller-owned Resources; UserResource no longer lazy-loads a role. Archive group payload parsing and persistence have one manager and payload helper. Schema capability lookups are cached across requests in a non-database cache store by default; bump `SCHEMA_CACHE_VERSION` after schema migrations.

The architecture target remains incomplete. A source scan still finds **205 `response()->json()` calls in 38 service files**, **178 schema capability check calls**, and **30 JSON encode/decode calls** in services. The persistent cache reduces repeated remote schema round trips, but it does not remove those checks or establish that every service returns only models, collections, or paginators. The remaining response and JSON paths need method-by-method migration with characterization coverage. No remote database was contacted, and no remote response-time improvement is claimed.

**Verdict: partially implemented; not ready to mark A1, A2, or A3 complete.** This audit supersedes the earlier completion statements in `REFACTOR_REPORT.md`. Application PHP code was not changed during this audit. No shared database or external delivery API was contacted.

## Evidence and limits

- The existing SQLite in-memory suite passes: **55 tests, 201 assertions** (`php artisan test --compact`).
- Five additional, database-free execution probes fail: construction of DisasterBroadcastService and ResourceRequestService; account recovery entry; broadcast event presentation; weather event presentation. Their errors are documented below.
- Reflection/source checks also identify unresolved method calls, inaccessible methods, and missing imports. These are separate findings from the passing suite; not every affected HTTP endpoint was exercised.
- The unauthenticated endpoint test returns 401 before the underlying authorized workflows execute (`tests/Feature/BackendEndpointCharacterizationTest.php:12`). It does not prove the authenticated service paths work.
- No before/after SQL query-count evidence was found in tests. No production query count, memory improvement, deployment compatibility, or external integration availability is asserted.
- Physical lines include blank lines. Previous counts used PowerShell `Measure-Object -Line`, which excluded blank lines and understated physical size. Some files also contain very long compressed methods: ResourceRequestWriteWorkflow has a 1,133-character line; RescueDispatchWorkflow has a 2,204-character line. Line count alone is insufficient evidence of separated responsibilities.

## Concrete A1/A2 boundary gaps

- `app/Services/Web/MappingService.php:24` and `app/Services/Web/NotificationService.php:27` construct response payloads. NotificationService still computes summary cards and manual pagination data.
- `app/Services/Web/DashboardService.php:75` builds dashboard arrays; line 98 implements cleanup writes. It is not orchestration only.
- `app/Services/Web/GlobalSearchService.php:29` returns display results, with model queries and row mapping from line 67; `matches()` at line 211 builds LIKE predicates.
- `app/Queries/InquiryListQuery.php:12` is a useful extracted read that returns a paginator. `app/Http/Controllers/Api/InquiryController.php:23` still returns the service's JsonResponse; there is no InquiryResource serialization boundary.
- `app/Queries/DashboardQuery.php:57` returns display cards/bars. `app/Queries/MappingQuery.php:59` calls a Presenter, then applies display status filtering. These query classes mix reading with presentation.
- `app/Queries/MappingQuery.php:63` calls `fallbackHouseholdStatusFromMembers()` per affected household; that helper runs another read at line 473. Batch fetch/group this source before presentation.
- `app/Presenters/ResourceRequestPresenter.php:29` calls `TrackingAidForwardingService::requestHandoffStatus()` for a row; that method performs a connection-specific schema check and SELECT at `app/Services/Shared/TrackingAidForwardingService.php:144`. Batch fetch the status data before formatting.
- `app/Http/Resources/UserResource.php:13` calls User::roleKey; `app/Models/User.php:110` loads a missing relationship. Eager loading at the query boundary plus conditional Resource output is still needed for a reliable zero-query serializer.
- `app/Presenters/WeatherSnapshotPresenter.php:130` still attempts database/schema access; a Presenter should receive that data from the read layer.
